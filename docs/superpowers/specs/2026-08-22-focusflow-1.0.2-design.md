# FocusFlow 1.0.2 Design

Date: 2026-08-22

**Parent spec:** `docs/superpowers/specs/2026-05-14-focusflow-ai-design.md`
**Related UI spec:** `docs/superpowers/specs/2026-05-31-focusflow-frontend-ui-design.md`

## Purpose

The parent spec and the shipped app treat plan generation as OPEN-only, with no ranking rules in the prompt, no plan delete endpoint, and no record of available focus time on a saved DailyPlan. This document specifies milestone **1.0.2**: users can delete a saved plan; generation considers in-progress work; the prompt states ranking rules; the backend enforces must-include blocks and leftover budget; and a shortfall warning is persisted so the user can see when the day cannot cover started and due/overdue work.

This is a design document, not an implementation plan. It amends the parent API shape and AI generation rules. It does not change the approved stack or the learning goal.

## Goals And Non-Goals

Goals:

- Let the owner hard-delete one DailyPlan (and its items) from plan detail and plan history, with the same confirmation pattern as task delete.
- Treat `OPEN` and `IN_PROGRESS` tasks as plannable. `DONE` and `CANCELLED` stay out of new plans.
- Put every in-progress task, then every due-or-overdue open task, into the new plan even when their estimates overflow available minutes.
- State ranking rules in the prompt (prefer HIGH, fit optional work in leftover minutes, must-include blocks).
- Reject an AI response that omits must-include work, breaks block order, or packs optional work that does not fit leftover. Do not silently repair the plan.
- Persist `availableMinutes` and a structured shortfall warning on DailyPlan so dashboard, history, and detail can show it after refresh.

Non-Goals:

- No remaining-minutes or progress field on Task.
- No soft-delete, archive, or cancel status on DailyPlan.
- No replace-on-generate: generating still inserts a new plan; older plans for the same date remain until the user deletes them.
- No backend-computed full ranking. The model still chooses optional work and intra-block order.
- No calendar integration, user preferences beyond these ranking rules, or changes to task delete.
- No required `estimatedMinutes` on tasks.

## Domain Language

**Plannable task**: A task that may appear in a new DailyPlan. Status is `OPEN` or `IN_PROGRESS`.
_Avoid:_ Active task, open task (when meaning the eligible set)

**Must-continue work**: Every plannable task with status `IN_PROGRESS`. Always present in the new DailyPlan.

**Due/overdue work**: Every remaining `OPEN` task whose `dueDate` is on or before `planDate`. Always present in the new DailyPlan.
_Avoid:_ Due today only (overdue is included)

**Optional work**: Every remaining `OPEN` task with no due date, or with `dueDate` after `planDate`. May be omitted.

**Must-include work**: Must-continue work plus due/overdue work. The union of generation blocks 1 and 2.

**Leftover minutes**: `availableMinutes` minus the sum of known `estimatedMinutes` on the candidate must-continue set and the candidate due/overdue set. A missing estimate costs 0. If that difference is negative, leftover is 0.
_Avoid:_ Remaining time (there is no remaining-minutes field)

**Shortfall warning**: A structured notice stored on the DailyPlan when known must-include estimates exceed `availableMinutes`, or when some must-include task has no estimate.

**Plan delete**: Hard delete of one DailyPlan and its items. Referenced Tasks are not deleted.

`planDate` is the date the plan is for. "Today" and "overdue" are relative to `planDate`, not the server clock.

## User Workflow

1. A user registers or logs in and manages tasks as today.
2. The user enters available focus minutes and generates a plan.
3. The backend loads the user's plannable tasks, calls the provider with ranking rules, validates the response, saves the plan (including available minutes and any shortfall warning), and returns it.
4. If the day cannot cover must-include work, the user sees the warning on the dashboard, the plan detail page, and as an indicator on the matching history row.
5. The user can delete a saved plan from plan detail or a history row after confirming. Tasks are unchanged. If that plan was the latest for its date, the dashboard shows the next latest plan for that date, or empty.

## Architecture

No new layers or packages. Plan delete, plannable-task loading, leftover validation, and warning persistence live in the existing `plan` and `ai` services. The frontend reuses the task-delete confirmation dialog pattern and the existing `DailyPlanView` surfaces.

DailyPlan gains two persisted fields: `availableMinutes` (nullable on rows created before 1.0.2; always set on new generates) and a structured warning (null when there is no shortfall). The warning is a snapshot from generate time. Plan items still reference live Tasks, so later task edits can disagree with the frozen warning; that is accepted.

## API Shape

This milestone adds one endpoint and extends the daily-plan response. Existing generate, list, and get-by-id paths stay.

- `DELETE /api/daily-plans/{id}` — owner-scoped hard delete. Success is `204`. Missing or another user's plan is `404` with the same error body as task delete. CSRF follows other state-changing requests.
- `POST /api/daily-plans/generate` — unchanged request (`availableMinutes`, optional `planDate`). Response is the extended `DailyPlanResponse`.
- `GET /api/daily-plans` and `GET /api/daily-plans/{id}` — return the extended `DailyPlanResponse` so clients can render `availableMinutes` and `warning` after refresh.

Extended `DailyPlanResponse`:

- Existing: `id`, `planDate`, `createdAt`, `items`
- Added: `availableMinutes` (`integer | null`)
- Added: `warning` (`DailyPlanWarning | null`)

`DailyPlanWarning`:

- `minimumAvailableMinutes` — sum of known `estimatedMinutes` on must-include candidate tasks at generate time
- `estimatedTasks` — those must-include tasks that had an estimate: `taskId`, `title`, `estimatedMinutes`
- `unestimatedTasks` — those must-include tasks that had no estimate: `taskId`, `title`

`warning` is non-null when `unestimatedTasks` is non-empty, or when `availableMinutes` is less than `minimumAvailableMinutes`. It is null when every must-include task had an estimate and `availableMinutes` covers that total.

Plans saved before 1.0.2 have `availableMinutes: null` and `warning: null`. The UI hides the warning in that case.

## Plan Delete

Deleting a plan removes that DailyPlan row and its DailyPlanItems only. Tasks stay.

The user confirms first, with the same dialog tone as task delete. Delete actions exist on **plan detail** and on each **history row**. The dashboard does not have its own delete control.

After a successful delete from detail, the client navigates to `/plans`. After a successful delete from history, the history list refreshes in place.

If the deleted plan was the latest for that `planDate`, list and dashboard fall back to the next latest plan for that date (existing `createdAt` descending order), or to the empty state.

## AI Plan Generation

When a user generates a plan:

1. Resolve `planDate` (request value, or today when omitted).
2. Load plannable tasks for the current user (`OPEN` and `IN_PROGRESS`). If that list is empty, return `400` with message `no plannable tasks available for planning` and do not call the provider. `IN_PROGRESS` only is valid and proceeds.
3. Classify candidates:
   - Block 1 (must-continue): status `IN_PROGRESS`
   - Block 2 (due/overdue): status `OPEN` and `dueDate <= planDate`
   - Block 3 eligible (optional): status `OPEN` and (`dueDate` is null or `dueDate > planDate`)
4. Build the prompt from those tasks (including status) plus ranking rules and available minutes.
5. Call the provider. Expect JSON items with `taskId` and `position`, as today.
6. Validate the response (see below). On failure, return `502` and do not save.
7. Save the DailyPlan, items, `availableMinutes`, and warning snapshot. Return the extended response.

### Ranking rules in the prompt

The prompt still lists each candidate as a line with id, title, priority, description, due date, and estimated minutes when present. It also includes status. It states:

- Prefer HIGH over MEDIUM over LOW.
- Sooner due date is a tiebreaker only when priority is equal. Title and description are used only when both of those are equal.
- Include every must-continue task, then every due/overdue open task, then optional work.
- Optional work must fit leftover minutes. The model may leave unused leftover rather than squeeze in a lower-priority task.
- Prefer tasks that have estimates. Do not pile unestimated optional tasks.
- Return an ordered plan using only the listed task ids, in the existing JSON shape.

Intended sort inside block 1 is HIGH, then sooner due date. Intended sort inside block 2 is sooner due date, then HIGH. Those sorts are prompt guidance only.

### Validation (reject, do not repair)

Leftover is computed from the **candidate** must-include sets (block 1 union block 2), not from the model output:

`leftover = max(0, availableMinutes - sum of known estimatedMinutes on block 1 and block 2 candidates)`

Reject the provider response when any of the following is true:

- A task id is not in the plannable candidate set (existing rule).
- Any block 1 candidate is missing from the items.
- Any block 2 candidate is missing from the items.
- Walking the items in order, a later-block item appears before an earlier-block item (block numbers 1, then 2, then 3).
- The sum of known `estimatedMinutes` on optional (block 3) items in the response is greater than leftover.

Do not reject intra-block sort mistakes. Do not reorder items. Unestimated optional items cost 0 toward the optional sum, so they "fit" even when leftover is 0; the prompt discourages piling them.

Must-continue and due/overdue items may overflow leftover. They are still required. Overflow is communicated with the shortfall warning, not with a generate failure.

## Error Handling

Existing status codes stay:

- `400 Bad Request` — validation errors, and generate with no plannable tasks (`no plannable tasks available for planning`).
- `401 Unauthorized` — unauthenticated requests.
- `403 Forbidden` — authenticated users attempting forbidden actions.
- `404 Not Found` — missing user-owned records, including delete of an unknown or other-user plan.
- `502 Bad Gateway` — provider failures and invalid provider output, including the new ranking-validation failures. Nothing is saved.

## Frontend

Follow the UI spec's confirmation, toast, alert, and query-invalidation patterns.

- Plan history rows and plan detail gain a delete action that opens the existing style of confirm dialog. Only on confirm is `DELETE /api/daily-plans/{id}` sent. Success toast; invalidate plan list and today's-plan queries. Detail delete then navigates to `/plans`.
- Dashboard does not add a delete button on today's plan.
- When `warning` is non-null, show an inline alert above the plan timeline on the dashboard and on plan detail. The alert lists the estimated must-include tasks and `minimumAvailableMinutes`, and lists unestimated must-include tasks as unknown duration.
- When `warning` is non-null, the history row shows a short "Shortfall" indicator. The full warning text lives on detail (and on the dashboard if that plan is today's latest).
- Generate still shows provider/`400` errors as an inline alert in the generate card. The empty-generate copy follows the new 400 message.
- Task form does not add remaining minutes.

## Testing Strategy

Keep the existing backend and frontend testing style: JUnit 5 and Mockito at service level, Spring MVC tests for the new delete endpoint and generate error bodies, Testcontainers for persistence of delete cascade and of `availableMinutes`/warning, and frontend component/hook tests for delete confirmation and warning rendering.

Highest-priority coverage:

- Delete is owner-scoped; other users get 404; items are removed; tasks remain.
- Generate with only `IN_PROGRESS` tasks succeeds; generate with no plannable tasks returns 400 and does not call the provider.
- A response that omits must-continue or due/overdue work, breaks block order, or overfills leftover with optional work is rejected and not saved.
- Intra-block mis-order is accepted and saved as returned.
- Warning is persisted when must-include work overflows or lacks estimates, and is null otherwise.
- Frontend delete does not fire until confirm; warning alert renders when the response includes `warning`.

## Learning Priorities

Unchanged from the parent spec. This milestone should teach owner-scoped delete, prompt-plus-validation at a service boundary, and persisting a small snapshot (available minutes and warning) next to an existing aggregate.

## Suggested Decomposition

This spec is one milestone. A later implementation plan can split it without changing the product rules:

1. Plan delete API and UI.
2. Plannable query, prompt ranking rules, and generate validation.
3. Persist `availableMinutes` and warning; render them on dashboard, history, and detail.
