## Purpose

Through 1.0.2 the schema has been maintained by hand: `application.yml` sets `ddl-auto: none`, and the README instructs contributors to export `SPRING_JPA_HIBERNATE_DDL_AUTO=update` and restart whenever a milestone adds columns. Nothing records what changed, nothing verifies that the entities and the database agree, and integration tests build their schema from entities rather than from whatever production actually ran.

The next two milestones (1.2.0 and 1.3.0) reshape the plan aggregate substantially — timed blocks, break blocks, user preferences, fixed commitments, and recorded actuals. Doing that on a hand-managed schema is where the current approach stops being merely untidy and starts losing data.

This milestone therefore adds no product capability. It hardens FocusFlow as a single-instance learning application with production-safe foundations: versioned migrations that are verified by the test suite, a provider call that cannot hang or hold a database transaction open, list endpoints that do not grow without bound, an API contract that cannot drift from the code, and enough observability to diagnose a failure from a single request id. It does not claim full enterprise operations.

One visible change follows unavoidably from paginating plan history: the page needs navigation, because a user with more saved plans than one page must still be able to reach the older ones. That is the only interface change in the milestone.

This is a design document, not an implementation plan.

## Goals And Non-Goals

Goals:

- Manage the schema with Flyway. Create the current schema as `V1`, adopt an existing verified 1.0.2 schema only through an explicit one-time procedure, retire `ddl-auto` as a deployment step, and make the test suite run the real migrations.
- Prove entities and schema agree by running Hibernate schema validation against the migrated database in tests.
- Give the AI provider call explicit connect and read timeouts, plus a conservative retry that avoids ambiguous failures that may already have incurred provider cost.
- Keep provider calls and retry delays outside database transactions; persist a validated plan in one short transaction.
- Replace the plan-history payload with a summary projection and paginate it.
- Split today's-plan reads onto their own endpoint so one endpoint no longer serves two response shapes.
- Make `planDate` explicit at the backend boundary rather than inferring "today" from the server clock.
- Generate the OpenAPI contract from code and fail the build when the committed copy is stale.
- Add separate liveness and readiness health endpoints, a request-id correlation filter, and bounded provider/ranking metrics, with a deliberately minimal unauthenticated surface.

Non-Goals:

- No new product capability. The dashboard, task management, plan generation, and plan detail behave as they do in 1.0.2. Plan history gains page navigation and nothing else.
- No audit timestamps (`createdAt`/`updatedAt`) and no `@Version` optimistic locking on any entity.
- No rate limiting or per-user cost cap on plan generation.
- No pagination of `GET /api/tasks`.
- No structured JSON logging. Local development keeps a readable plain-text pattern.
- No externally supported API or compatibility window. The REST API is a first-party product API consumed by the FocusFlow frontend, and frontend/backend contract changes ship atomically.
- No Prometheus endpoint, dashboards, alerts, service-level objectives, or production monitoring claim.
- No change to authentication, session handling, CSRF, or the ranking and warning rules from 1.0.2.
- Nothing from the 1.2.0 scheduling design: no clock times, breaks, preferences, commitments, or actuals.

## Domain Language

**Baseline migration**: `V1`, the migration that creates the canonical schema as it exists at the end of 1.0.2. A fresh database runs it; an existing verified 1.0.2 database adopts its version through a separate legacy-schema-adoption procedure.
_Avoid:_ Adoption migration

**Legacy schema adoption**: The explicit, one-time operation that records a verified pre-Flyway 1.0.2 database as already being at V1. It is never an automatic property of normal application startup.
_Avoid:_ Automatic baseline

**Plan summary**: The reduced view of a DailyPlan used by plan history — identity, date, creation time, available minutes, a count of items, and whether a shortfall warning exists. It carries no items and no tasks.

**Plan detail**: The existing full `DailyPlanResponse`, with items and their nested tasks. Returned by get-by-id, generate, and the new latest-plan read.

**Latest plan for a date**: The most recently created DailyPlan whose `planDate` matches. 1.0.2 permits several plans per date, so "latest" is ordered by `createdAt` descending, then `id` descending.

**Planning date**: The explicit calendar date for which a plan is generated or read. The client supplies it; the backend does not infer "today" from its own clock.
_Avoid:_ Server date, today (at an API boundary)

**Generation snapshot**: The candidate task state used to rank and validate one generation attempt. Later edits do not retroactively change that attempt; if a selected task disappears before persistence, the attempt fails and saves no plan.

**First-party product API**: The REST contract supported for FocusFlow's own frontend. Frontend and backend change atomically; compatibility for independent external clients is not promised until an external API is explicitly launched.

**Request id**: A correlation value carried per HTTP request. A valid inbound `X-Request-Id` is reused; otherwise the application generates one. The response header is canonical for every outcome, and existing application error JSON repeats it.

**Page envelope**: The response wrapper for a paginated list — content plus page number, page size, total elements, and total pages. An explicit DTO, not a serialized Spring Data `Page`.

## Architecture

No change to the layered model. Controllers delegate to services, services own transactions, repositories persist, and cross-feature reads go through facades. Two small packages appear:

- `common/web` — the `PageResponse` envelope, shared by any future paginated endpoint.
- `common/observability` — the request-id filter.

`backend/src/main/resources/db/migration` is new and becomes the only place schema changes are expressed.

Plan generation is split into two boundaries. Non-transactional orchestration loads a generation snapshot, calls and—when permitted—retries the provider, and validates its ordering. A short transactional persistence operation then reloads the selected owner-scoped task references and saves the plan atomically. If a selected task was deleted between snapshot and persistence, the operation returns **409 Conflict** and saves nothing. Other task edits do not invalidate the snapshot; this preserves the existing rule that saved plan items reference live Tasks while warning and generation decisions describe generate-time state.

One existing architecture rule constrains the pagination design. `LayeredArchitectureTest` enforces that no class whose name ends in `Repository` may depend on anything in a `..dto..` package:

```java
noClasses().that().haveSimpleNameEndingWith("Repository")
    .should().dependOnClassesThat().resideInAPackage("..dto..")
```

A JPQL constructor expression or a projection typed directly to `DailyPlanSummaryResponse` would break that rule, because the response DTO lives in `plan.dto`. So the repository returns a Spring Data interface projection — `DailyPlanSummaryProjection`, declared in `com.focusflow.plan` alongside the entities — and `DailyPlanService` maps that projection to `DailyPlanSummaryResponse`. The rule stays intact and the DTO boundary stays where the rest of the codebase puts it.

The new `common` packages do not weaken or bypass the existing architecture rules.

## Schema Migrations

Add `flyway-core` and `flyway-database-postgresql`. Since Flyway 10 the PostgreSQL dialect lives in its own module, and Spring Boot 3.4 manages both versions.

The explicit adoption policy is recorded in `docs/adr/0001-explicit-legacy-schema-adoption.md` because writing Flyway history into an existing database is difficult to reverse and normal auto-baselining would look deceptively convenient to a future maintainer.

`V1__baseline.sql` reproduces the schema as of 1.0.2:

| Table | Columns and constraints |
|---|---|
| `users` | identity `id`; `email` and `username` both non-null and unique; `password_hash` non-null, length 255 |
| `tasks` | identity `id`; `owner_id` non-null, foreign key to `users`; `title` non-null; `description` as `TEXT`; `priority` and `status` non-null `varchar(32)`; nullable `due_date`; nullable `estimated_minutes` |
| `daily_plans` | identity `id`; `owner_id` non-null, foreign key to `users`; `plan_date` non-null; `created_at` non-null; nullable `available_minutes`; nullable `warning` as `jsonb` |
| `daily_plan_items` | identity `id`; `daily_plan_id` non-null, foreign key to `daily_plans`; `task_id` non-null, foreign key to `tasks`; `position` non-null |

Indexes on the owner-scoped access paths belong in `V1` as well, since every read in the application filters by `owner_id`, and plan history additionally orders by `created_at` then `id`.

Configuration and adoption:

- `spring.flyway.baseline-on-migrate` is false in every normal application profile. An unexpected non-empty database without Flyway history must stop startup rather than be silently declared valid.
- A fresh database runs `V1` normally.
- Adopting a pre-Flyway 1.0.2 database is an explicit one-time operation. The operator first takes a backup and runs a read-only preflight that verifies the expected tables, columns, foreign keys, unique constraints, indexes, and column types. Only a passing schema is baselined at version 1. Normal startup then resumes with automatic baselining still disabled.
- The adoption command/profile must not be a general deployment setting or remain enabled after use. The exact command and recovery procedure belong in the README.
- Flyway migrations are forward-only. Recovery from a failed legacy adoption uses the pre-adoption backup; no down migration is promised.
- `ddl-auto` stays `none` in the default profile and stops being something a contributor sets by hand. The README instructions that describe exporting `update` are removed.

### Test schema

Tests run the real migrations and then assert the entities match them. `application-test.yml` sets `ddl-auto: validate`, so Hibernate compares every mapped entity against the migrated schema at context startup and fails the context when they disagree. A missing migration for a new entity field fails the build, and so does a migration that got a type or nullability wrong.

Two test-infrastructure changes make that work:

`PostgresIntegrationTest` currently forces schema creation from entities:

```java
registry.add("spring.jpa.hibernate.ddl-auto", () -> "create-drop");
```

That override is removed so Flyway owns the test schema.

More importantly, `FocusFlowApplicationTests` is a plain `@SpringBootTest` with no container — it inherits the `application-test.yml` datasource pointing at local Postgres. Flyway migrates eagerly during context startup, so once Flyway is present this test requires a reachable database where it previously might not have connected at all. Rather than special-casing it, both `@SpringBootTest` classes should share one container through Spring Boot's `@ServiceConnection` support (which needs the `spring-boot-testcontainers` test dependency). That replaces the hand-rolled `@DynamicPropertySource` block, gives both tests the same migrated schema, and keeps the Windows Docker strategy workaround in one place.

## Provider Reliability

`OpenAiClientConfiguration` currently builds the client with no timeouts at all:

```java
return RestClient.builder().baseUrl(properties.baseUrl()).build();
```

A provider that accepts the connection and never responds holds a request thread indefinitely. The client gets an explicit request factory with a short connect timeout and a generous read timeout, because chat completions legitimately take many seconds.

`OpenAiProperties` gains `connectTimeout`, `readTimeout`, `maxAttempts`, `retryDelay`, and `maxRetryAfter`, defaulted in its compact constructor the same way `baseUrl` already is, and overridable through `focusflow.openai.*` so tests can pin them to fast values and one attempt.

Retry is deliberately narrow, because every attempt costs money:

- At most `maxAttempts` attempts in total, defaulting to 2.
- Retry a connection-establishment failure, where no HTTP response was received.
- Retry only explicit transient responses: HTTP 429, 502, 503, and 504.
- Honor `Retry-After` when present, but cap it at `maxRetryAfter`; otherwise use the configured fixed delay.
- Never retry a read timeout. The provider may have finished and charged for the response after FocusFlow stopped waiting, so retrying would risk paying twice for one user action.
- Never retry HTTP 500, any other 4xx, a malformed response, or ranking rejection. An invalid or missing API key must fail on the first attempt rather than spend a second call confirming it.

This lives as explicit code inside `OpenAiDailyPlanClient` rather than behind Spring Retry annotations. The interesting part of this feature is the predicate deciding what is worth retrying, and that predicate should be readable at the call site. The client already funnels every failure into `AiProviderException`, so the external contract is unchanged: exhausted retries still surface as **502**.

The provider call and any retry delay run outside a database transaction. Only the final validated persistence step opens a transaction.

## API Shape

The REST API is a first-party product API consumed by the FocusFlow frontend. This release changes frontend and backend atomically; it does not carry both old and new plan-list contracts for hypothetical external clients.

**`GET /api/daily-plans`** — now a paginated list of plan summaries.

- Query parameters: `page` (default 0, minimum 0), `size` (default 20, minimum 1, maximum 100), and the existing optional `planDate` filter.
- A `size` above the maximum is rejected with **400** rather than silently clamped, so a client is never told it received a full page when it did not.
- Sort order is fixed at `createdAt` descending, then `id` descending, and is not client-controlled. The id tie-breaker makes ordering deterministic when two plans have the same creation timestamp.
- Response is `PageResponse<DailyPlanSummaryResponse>`.
- Page totals describe the database at the time of each request. Generating or deleting a plan between requests may shift later offset-based pages; this is accepted for plan-history scale.

`DailyPlanSummaryResponse`: `id`, `planDate`, `createdAt`, `availableMinutes` (`integer | null`), `itemCount`, `hasWarning`.

`PageResponse<T>`: `content`, `page`, `size`, `totalElements`, `totalPages`. An explicit DTO, because serializing Spring Data's `Page` directly is unstable across versions and Boot warns against it.

**`POST /api/daily-plans/generate`** — existing path, tightened request contract.

- `planDate` becomes required alongside `availableMinutes`.
- A missing `planDate` returns **400**. The first-party frontend already supplies its browser-local calendar date.
- The backend no longer substitutes `LocalDate.now()`, avoiding disagreement between browser and server timezones.

**`GET /api/daily-plans/latest`** — new. Returns plan detail for the latest plan on a date.

- Required `planDate` query parameter. A missing value returns **400**.
- **200** with the full `DailyPlanResponse` when a plan exists.
- **204 No Content** when none exists. Having no plan yet is an ordinary state, not a failure; a 404 would make the frontend treat an unremarkable morning as an error.

Because `/{id}` binds a `Long`, the literal `latest` segment must win path resolution. Spring's pattern comparator prefers a literal over a variable, so this resolves correctly, but it is subtle enough to deserve an explicit test rather than an assumption.

**`GET /api/daily-plans/{id}`** and **`DELETE /api/daily-plans/{id}`** — unchanged, returning or operating on plan detail as today.

`GET /actuator/health/liveness` and `GET /actuator/health/readiness` — public with component details hidden. The aggregate health endpoint and every other Actuator endpoint require a session.

`/v3/api-docs` and the Swagger UI paths — present only under the `dev` profile.

### Repository impact

The summary list is served by projection queries returning `Page<DailyPlanSummaryProjection>` — one for the unfiltered list and one for the `planDate`-filtered list — so items and their tasks are never loaded for a history page. `itemCount` comes from a count over the item association rather than from a loaded collection.

The `@EntityGraph` and `SELECT DISTINCT` that `findAllByOwner_IdOrderByCreatedAtDesc` and `findByOwner_IdAndPlanDateOrderByCreatedAtDesc` carry today are removed along with those methods — that is the exact code behind issue 4 in `docs/implementation-issues.md`, and deleting it is safe only because nothing maps items on that path any more.

The fetch graph survives where it is genuinely required: `findByOwner_IdAndId` for detail, and a new graph-backed `findFirstByOwner_IdAndPlanDateOrderByCreatedAtDescIdDesc` for the latest-plan read.

## Generated API Contract

Add `springdoc-openapi-starter-webmvc-ui`. Most of the contract is inferred from the existing request and response records and their Bean Validation annotations; controllers need only enough annotation to describe status codes that springdoc cannot infer, such as the 204 on the latest-plan read.

`/v3/api-docs` and Swagger UI are disabled in the default profile and enabled in a new `application-dev.yml`.

The hand-maintained `docs/openapi.yaml` is replaced by a generated canonical snapshot, committed so the contract remains reviewable in diffs. A dedicated integration test starts the ordinary Testcontainers-backed Spring context with springdoc enabled, obtains the generated document, normalizes deterministic ordering and formatting, and compares it with the committed snapshot. Ordinary tests never write repository files. A separate explicit update command rewrites the snapshot when an intentional API change is made. CI fails on a mismatch, which makes drift impossible without starting a separate `bootRun` process or managing a CI port.

`docs/api.md` stays hand-written. It explains session and CSRF calling rules and shows worked examples — a calling guide, not a schema dump. It still needs editing in this milestone, because it documents the daily-plan list response that is becoming a page of summaries and gains the latest-plan endpoint. Its link to the OpenAPI file and the README's documentation section are updated to describe the generated artifact and the dev-profile Swagger UI, and the README's manual verification checklist picks up the 204 case.

## Observability

Add `spring-boot-starter-actuator`, exposing health and metrics only.

A `RequestIdFilter` in `common/observability` runs early in the chain. It accepts an inbound `X-Request-Id` only when it matches `[A-Za-z0-9._-]{1,64}`; otherwise it generates a UUID. It puts the chosen value in the logging MDC, echoes it on every response header, and clears the MDC in a `finally` block so nothing leaks between pooled request threads. A `logback-spring.xml` adds the value to the existing readable console pattern.

The `X-Request-Id` response header is the canonical correlation contract because the filter can add it even when Spring Security rejects a request before a controller runs. `ApiErrorResponse` also gains a nullable `requestId`, supplied by `GlobalExceptionHandler` from the MDC for application errors that already use that JSON shape. This milestone does not replace Spring Security's existing empty 401/403 handlers merely to put an id in their body. The record is already annotated `@JsonInclude(NON_NULL)`, so the added field is backward compatible for clients that ignore unknown fields.

Micrometer, which arrives with Actuator, records:

- A timer around the provider call, tagged by outcome — success, provider error, or invalid response.
- A counter for retried attempts.
- A counter for ranking-validation rejections, tagged by reason.

Every tag value comes from a bounded enum or fixed set; exception messages, task ids, request ids, paths containing ids, and provider response text are never metric tags. The ranking-rejection reason therefore becomes a typed, bounded classification rather than being derived from the current free-form exception message.

That last metric matters directly to the next milestone. 1.2.0 keeps the AI responsible for ordering while Java takes over placement, and the decision to keep trusting the model for ranking should rest on measured rejection rates rather than impressions.

Health is split by purpose:

- `/actuator/health/liveness` reports whether the application process can continue. It excludes PostgreSQL and other external dependencies so an outage does not trigger a JVM restart loop.
- `/actuator/health/readiness` includes PostgreSQL and reports whether the instance can accept useful traffic.
- Public health responses never expose component details.
- `/actuator/metrics` remains available only to an authenticated session for manual diagnosis.

Prometheus, machine-to-machine scrape authentication, dashboards, alerts, and service-level objectives are deferred. This is a diagnostic foundation, not a claim of complete production monitoring.

## Security Exposure

`SecurityConfig` today permits register and login and requires authentication for everything else, with a 401 entry point. Two additions:

- `/actuator/health/liveness` and `/actuator/health/readiness` are explicitly permitted, ahead of the `anyRequest().authenticated()` rule, so an orchestrator can probe the application without credentials. The aggregate health endpoint and every other Actuator endpoint fall through to requiring a session, keeping component and metric data private.
- The springdoc paths are permitted by a separate, higher-precedence `SecurityFilterChain` bean annotated `@Profile("dev")`, whose security matcher covers only `/v3/api-docs/**` and `/swagger-ui/**`. Under the default profile that bean does not exist, so there is no permissive rule to audit and no accidental production exposure. The main chain keeps its ordering, its CSRF configuration, and `CsrfCookieFilter`.

## Error Handling

Status codes remain consistent with the existing contract: **400** for validation failures including missing planning dates and pagination bounds, **401** unauthenticated, **403** forbidden, **404** for missing owner-scoped records, **409** for conflicts including a selected task disappearing before plan persistence, and **502** for provider failures including exhausted retries.

`ApiErrorResponse` gains the nullable `requestId`. The response header, not the JSON field, is the request-id guarantee shared by application and Spring Security errors.

## Frontend

Changes are mechanical. Page navigation on plan history is the only one a user notices; everything else is the same screens fed from different endpoints.

- Plan history reads `itemCount` and `hasWarning` from the summary instead of deriving them from a full item array. `PlanHistoryList` currently renders `plan.items.length` and `plan.warning != null` and touches nothing else on a row, so the row markup is unaffected.
- Plan history consumes the page envelope and gains navigation between pages, driven by the envelope's `page` and `totalPages`. Without it, paginating the endpoint would silently hide older plans from anyone holding more than one page of them. Previous and next controls are enough; the list is chronological and has no search or filtering to preserve.
- The dashboard's today's-plan hook moves to `GET /api/daily-plans/latest?planDate=...`, explicitly sends the browser-local calendar date, and maps **204** to an absent plan, feeding the existing empty state in `DailyPlanView`.
- Plan generation continues sending the browser-local `planDate`, which is now required rather than merely accepted.
- `frontend/src/types/api.ts` gains `DailyPlanSummaryResponse` and `PageResponse<T>`, and the plan history type changes from `DailyPlanResponse[]`.
- Query keys and invalidation follow the existing pattern: generate and delete continue to invalidate both the history list and the latest-plan query.

## Testing Strategy

The existing style holds — Mockito for service behaviour, `@WebMvcTest` for HTTP and security boundaries, Testcontainers for persistence, ArchUnit for layering, and Vitest on the frontend.

The most valuable property this milestone adds is that migrations become self-checking. With Flyway plus `validate` running in the shared container, an entity field with no matching migration fails the build rather than surfacing later as a runtime error against a real database.

Highest-priority coverage:

- The application context starts against a migrated container with `validate` active, for both `@SpringBootTest` classes.
- A fresh database runs V1, normal startup rejects a non-empty unversioned schema, the adoption preflight rejects a structural mismatch, and an explicitly verified 1.0.2 schema can be baselined once.
- Retry attempts the configured maximum on connection establishment failures and 429/502/503/504, honors a bounded `Retry-After`, and makes one attempt only on a read timeout, 500, 401, malformed response, or ranking rejection — asserted by attempt count against a stub server, since the cost behaviour is the point.
- The provider client is invoked without an active database transaction; persistence opens one short transaction after validation.
- An exhausted retry still surfaces as **502** and persists no plan, preserving the 1.0.2 guarantee.
- A selected task deleted before persistence produces **409** and saves no partial plan.
- The summary list returns correct `itemCount` and `hasWarning` values, and loads no items — verified by a persistence test that reads summaries outside the repository transaction, which would have caught issue 4 directly.
- Pagination defaults apply, `size` above the maximum returns **400**, and equal timestamps are ordered by id descending.
- Generate and latest-plan requests without `planDate` return **400**. The latest-plan endpoint returns **204** when no plan exists for the supplied date, and the newest plan when several exist; `/latest` resolves to its own handler rather than binding as an `{id}`.
- The canonical OpenAPI document produced by the Testcontainers-backed integration context matches `docs/openapi.yaml`; the update command is deterministic and ordinary tests never write the file.
- Liveness and readiness answer unauthenticated without details, readiness fails when PostgreSQL is unavailable, liveness does not, `/actuator/metrics` returns **401** unauthenticated, and springdoc paths are absent without the `dev` profile.
- The request-id filter echoes a valid inbound `X-Request-Id`, replaces an absent or invalid one, returns the chosen id even on a Spring Security failure, and puts it in `ApiErrorResponse` where that body exists.
- Frontend: plan history renders from summaries; page navigation requests the next page and disables itself on the first and last page; the dashboard shows its empty state on a 204.

## Risks

**Schema validation will surface existing drift all at once.** `validate` is strict about column types, lengths, and nullability. The `jsonb` warning column and the `varchar(32)` enum columns are the likely first offenders, so writing `V1` is an iterative exercise against a real database rather than a transcription of the entity classes. This is the milestone doing its job, but it should be planned as real work rather than a quick first step.

**Legacy adoption is an operator action, not an application convenience.** A mistaken baseline permanently changes how Flyway interprets the database's history. The preflight, backup, explicit opt-in, and immediate return to `baseline-on-migrate: false` are part of the acceptance criteria, not optional README polish.

**Flyway makes a database mandatory at context startup.** Any `@SpringBootTest` now needs a reachable migrated database. The shared container addresses the two current cases; any new full-context test must use the same fixture.

**The shorter transaction introduces a concurrency window.** Task state can change while the provider is running. Generation decisions use the captured snapshot; deletion of a selected task aborts persistence with 409, while ordinary edits are visible through the existing live Task reference after save. Full optimistic concurrency remains deferred.

**Removing the fetch graph is only safe together with the summary DTO.** If the projection and the graph removal land in separate steps in the wrong order, plan history regresses straight back to issue 4. They belong in one step.

**The OpenAPI freshness check can become noise.** If the generated document is not deterministic across runs, the CI check will fail on unrelated changes. Ordering needs to be stable before the check is enforced.

## Learning Priorities

Consistent with the parent spec, weighted toward operational Java and Spring practice rather than new domain modelling: versioned schema management and the difference between a baseline and a migration; Hibernate schema validation as a build-time guarantee; HTTP client timeout and retry design where retries cost money; Spring Data projections and pagination, and why a projection is preferable to fetching an aggregate you will not use; profile-scoped security configuration; and MDC-based request correlation.

## Suggested Decomposition

This milestone splits cleanly into steps that can each be verified on their own. Steps 2 through 5 depend on step 1 only for the ability to express schema changes, and none of them changes the others' behaviour.

1. **Flyway and the test fixture.** Dependencies, canonical `V1`, explicit legacy-adoption preflight and procedure, the shared `@ServiceConnection` container, `validate` in the test profile, removal of the `create-drop` override, and the README `ddl-auto` cleanup. Resolving validation mismatches belongs here.
2. **Provider reliability and transaction boundaries.** Properties, request factory, conservative retry predicate, attempt-count tests, non-transactional orchestration, and short transactional persistence.
3. **Plan summaries, pagination, and explicit planning dates.** Projection, `PageResponse`, deterministic ordering, required `planDate`, the latest endpoint, repository cleanup, and matching frontend changes. The projection and the fetch-graph removal must land together.
4. **Generated OpenAPI.** springdoc, the dev profile, canonical snapshot integration test, explicit update command, CI freshness enforcement, and documentation link updates.
5. **Diagnostic observability.** Actuator liveness/readiness, security rules, request-id validation and its appearance on `ApiErrorResponse`, the Logback pattern, bounded provider/ranking metrics, and explicit exclusion of Prometheus-level operations.

A type-1 plan derived from this spec should be marked **TDD suitable: partial**. The retry predicate, transaction boundary, summary projection, pagination bounds, explicit-date validation, latest-plan status behaviour, request-id filter, health groups, and security rules are all naturally test-first. Writing `V1`, adding dependencies, and wiring the OpenAPI update command are not.

## Roadmap Beyond 1.1.0

This spec is the first milestone of a larger iteration. The remaining milestones (1.2.0 — the scheduled day, 1.3.0 — progress and carry-over, 1.4.0 — dependencies and the multi-day horizon), the cross-milestone scheduling decisions already settled, and the deferred backlog are tracked in [`docs/superpowers/roadmap.md`](../roadmap.md) rather than duplicated here, so one document stays current as each later milestone is brainstormed and specced.
