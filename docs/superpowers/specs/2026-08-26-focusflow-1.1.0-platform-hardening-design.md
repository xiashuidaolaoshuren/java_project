# FocusFlow 1.1.0 Design — Platform Hardening

Date: 2026-08-26

**Parent spec:** `docs/superpowers/specs/2026-05-14-focusflow-ai-design.md`
**Previous milestone:** `docs/superpowers/specs/2026-08-22-focusflow-1.0.2-design.md`
**Related UI spec:** `docs/superpowers/specs/2026-05-31-focusflow-frontend-ui-design.md`

## Purpose

Through 1.0.2 the schema has been maintained by hand: `application.yml` sets `ddl-auto: none`, and the README instructs contributors to export `SPRING_JPA_HIBERNATE_DDL_AUTO=update` and restart whenever a milestone adds columns. Nothing records what changed, nothing verifies that the entities and the database agree, and integration tests build their schema from entities rather than from whatever production actually ran.

The next two milestones (1.2.0 and 1.3.0) reshape the plan aggregate substantially — timed blocks, break blocks, user preferences, fixed commitments, and recorded actuals. Doing that on a hand-managed schema is where the current approach stops being merely untidy and starts losing data.

This milestone therefore adds no product capability. It makes the platform trustworthy enough to carry the scheduling work: versioned migrations that are verified by the test suite, a provider call that cannot hang, list endpoints that do not grow without bound, an API contract that cannot drift from the code, and enough observability to diagnose a failure from a single request id.

One visible change follows unavoidably from paginating plan history: the page needs navigation, because a user with more saved plans than one page must still be able to reach the older ones. That is the only interface change in the milestone.

This is a design document, not an implementation plan.

## Goals And Non-Goals

Goals:

- Manage the schema with Flyway. Baseline the existing schema as `V1`, retire `ddl-auto` as a deployment step, and make the test suite run the real migrations.
- Prove entities and schema agree by running Hibernate schema validation against the migrated database in tests.
- Give the AI provider call explicit connect and read timeouts, plus a narrow retry that cannot multiply cost on a non-retryable failure.
- Replace the plan-history payload with a summary projection and paginate it.
- Split today's-plan reads onto their own endpoint so one endpoint no longer serves two response shapes.
- Generate the OpenAPI contract from code and fail the build when the committed copy is stale.
- Add Actuator, a request-id correlation filter, and provider metrics, with a deliberately minimal unauthenticated surface.

Non-Goals:

- No new product capability. The dashboard, task management, plan generation, and plan detail behave as they do in 1.0.2. Plan history gains page navigation and nothing else.
- No audit timestamps (`createdAt`/`updatedAt`) and no `@Version` optimistic locking on any entity.
- No rate limiting or per-user cost cap on plan generation.
- No pagination of `GET /api/tasks`.
- No structured JSON logging. Local development keeps a readable plain-text pattern.
- No change to authentication, session handling, CSRF, or the ranking and warning rules from 1.0.2.
- Nothing from the 1.2.0 scheduling design: no clock times, breaks, preferences, commitments, or actuals.

## Domain Language

**Baseline migration**: `V1`, the migration that reproduces the schema as it exists at the end of 1.0.2. Databases that already have that schema adopt it instead of running it.
_Avoid:_ Initial migration (it does not create anything on an existing database)

**Plan summary**: The reduced view of a DailyPlan used by plan history — identity, date, creation time, available minutes, a count of items, and whether a shortfall warning exists. It carries no items and no tasks.

**Plan detail**: The existing full `DailyPlanResponse`, with items and their nested tasks. Returned by get-by-id, generate, and the new latest-plan read.

**Latest plan for a date**: The most recently created DailyPlan whose `planDate` matches. 1.0.2 permits several plans per date, so "latest" is ordered by `createdAt` descending — the same rule the dashboard applies today.

**Request id**: A correlation value carried per HTTP request, taken from an inbound `X-Request-Id` header or generated when absent. Present in logs, on the response, and on error bodies.

**Page envelope**: The response wrapper for a paginated list — content plus page number, page size, total elements, and total pages. An explicit DTO, not a serialized Spring Data `Page`.

## Architecture

No change to the layered model. Controllers delegate to services, services own transactions, repositories persist, and cross-feature reads go through facades. Two small packages appear:

- `common/web` — the `PageResponse` envelope, shared by any future paginated endpoint.
- `common/observability` — the request-id filter.

`backend/src/main/resources/db/migration` is new and becomes the only place schema changes are expressed.

One existing architecture rule constrains the pagination design. `LayeredArchitectureTest` enforces that no class whose name ends in `Repository` may depend on anything in a `..dto..` package:

```java
noClasses().that().haveSimpleNameEndingWith("Repository")
    .should().dependOnClassesThat().resideInAPackage("..dto..")
```

A JPQL constructor expression or a projection typed directly to `DailyPlanSummaryResponse` would break that rule, because the response DTO lives in `plan.dto`. So the repository returns a Spring Data interface projection — `DailyPlanSummaryProjection`, declared in `com.focusflow.plan` alongside the entities — and `DailyPlanService` maps that projection to `DailyPlanSummaryResponse`. The rule stays intact and the DTO boundary stays where the rest of the codebase puts it.

`LayeredArchitectureTest` may need a rule extension for the new `common` packages; the existing rules should continue to pass unchanged.

## Schema Migrations

Add `flyway-core` and `flyway-database-postgresql`. Since Flyway 10 the PostgreSQL dialect lives in its own module, and Spring Boot 3.4 manages both versions.

`V1__baseline.sql` reproduces the schema as of 1.0.2:

| Table | Columns and constraints |
|---|---|
| `users` | identity `id`; `email` and `username` both non-null and unique; `password_hash` non-null, length 255 |
| `tasks` | identity `id`; `owner_id` non-null, foreign key to `users`; `title` non-null; `description` as `TEXT`; `priority` and `status` non-null `varchar(32)`; nullable `due_date`; nullable `estimated_minutes` |
| `daily_plans` | identity `id`; `owner_id` non-null, foreign key to `users`; `plan_date` non-null; `created_at` non-null; nullable `available_minutes`; nullable `warning` as `jsonb` |
| `daily_plan_items` | identity `id`; `daily_plan_id` non-null, foreign key to `daily_plans`; `task_id` non-null, foreign key to `tasks`; `position` non-null |

Indexes on the owner-scoped access paths belong in `V1` as well, since every read in the application filters by `owner_id`, and plan history additionally orders by `created_at`.

Configuration:

- `spring.flyway.baseline-on-migrate: true` with `baseline-version: 1`. An existing database already carrying this schema is marked as being at `V1` and the script is skipped; an empty database has no history table and runs `V1` normally. Either way the local Docker volume survives, which is why the baseline is preferred over recreating from scratch.
- `ddl-auto` stays `none` in the default profile and stops being something a contributor sets by hand. The README instructions that describe exporting `update` are removed.

### Test schema

Tests run the real migrations and then assert the entities match them. `application-test.yml` sets `ddl-auto: validate`, so Hibernate compares every mapped entity against the migrated schema at context startup and fails the context when they disagree. A missing migration for a new entity field fails the build, and so does a migration that got a type or nullability wrong.

Two test-infrastructure changes make that work:

`PostgresIntegrationTest` currently forces schema creation from entities:

```java
registry.add("spring.jpa.hibernate.ddl-auto", () -> "create-drop");
```

That override is removed so Flyway owns the test schema.

More importantly, `FocusFlowApplicationTests` is a plain `@SpringBootTest` with no container — it inherits the `application-test.yml` datasource pointing at local Postgres. Flyway migrates eagerly during context startup, so once Flyway is present this test requires a reachable database where it previously might not have connected at all. Rather than special-casing it, both `@SpringBootTest` classes should share one container through Spring Boot's `@ServiceConnection` support (which needs the `spring-boot-testcontainers` test dependency). That replaces the hand-rolled `@DynamicPropertySource` block, gives both tests the same migrated schema, and keeps the Windows Docker strategy workaround in one place.

## Provider Reliability

`OpenAiClientConfiguration` currently builds the client with no timeouts at all:

```java
return RestClient.builder().baseUrl(properties.baseUrl()).build();
```

A provider that accepts the connection and never responds holds a request thread indefinitely. The client gets an explicit request factory with a short connect timeout and a generous read timeout, because chat completions legitimately take many seconds.

`OpenAiProperties` gains `connectTimeout`, `readTimeout`, `maxAttempts`, and `retryDelay`, defaulted in its compact constructor the same way `baseUrl` already is, and overridable through `focusflow.openai.*` so tests can pin them to fast values and zero retries.

Retry is deliberately narrow, because every attempt costs money:

- At most `maxAttempts` attempts in total, defaulting to 2.
- Retry only on a connect failure, a read timeout, HTTP 429, or HTTP 5xx.
- Never retry any other 4xx. An invalid or missing API key must fail on the first attempt rather than spend a second call confirming it.
- A fixed short delay between attempts.

This lives as explicit code inside `OpenAiDailyPlanClient` rather than behind Spring Retry annotations. The interesting part of this feature is the predicate deciding what is worth retrying, and that predicate should be readable at the call site. The client already funnels every failure into `AiProviderException`, so the external contract is unchanged: exhausted retries still surface as **502**.

Response-parsing failures are not retried. A malformed body is a provider defect, not a transient condition.

## API Shape

Existing endpoints keep their paths and semantics except where stated. Nothing in the request contract for generate, task CRUD, or auth changes.

**`GET /api/daily-plans`** — now a paginated list of plan summaries.

- Query parameters: `page` (default 0, minimum 0), `size` (default 20, minimum 1, maximum 100), and the existing optional `planDate` filter.
- A `size` above the maximum is rejected with **400** rather than silently clamped, so a client is never told it received a full page when it did not.
- Sort order is fixed at `createdAt` descending and is not client-controlled. This keeps the contract small and the supporting index predictable.
- Response is `PageResponse<DailyPlanSummaryResponse>`.

`DailyPlanSummaryResponse`: `id`, `planDate`, `createdAt`, `availableMinutes` (`integer | null`), `itemCount`, `hasWarning`.

`PageResponse<T>`: `content`, `page`, `size`, `totalElements`, `totalPages`. An explicit DTO, because serializing Spring Data's `Page` directly is unstable across versions and Boot warns against it.

**`GET /api/daily-plans/latest`** — new. Returns plan detail for the latest plan on a date.

- Optional `planDate` query parameter, defaulting to today, matching how `planDate` is resolved on generate.
- **200** with the full `DailyPlanResponse` when a plan exists.
- **204 No Content** when none exists. Having no plan yet is an ordinary state, not a failure; a 404 would make the frontend treat an unremarkable morning as an error.

Because `/{id}` binds a `Long`, the literal `latest` segment must win path resolution. Spring's pattern comparator prefers a literal over a variable, so this resolves correctly, but it is subtle enough to deserve an explicit test rather than an assumption.

**`GET /api/daily-plans/{id}`**, **`POST /api/daily-plans/generate`**, **`DELETE /api/daily-plans/{id}`** — unchanged, all returning or operating on plan detail as today.

`GET /actuator/health` — public. Every other Actuator endpoint requires a session.

`/v3/api-docs` and the Swagger UI paths — present only under the `dev` profile.

### Repository impact

The summary list is served by projection queries returning `Page<DailyPlanSummaryProjection>` — one for the unfiltered list and one for the `planDate`-filtered list — so items and their tasks are never loaded for a history page. `itemCount` comes from a count over the item association rather than from a loaded collection.

The `@EntityGraph` and `SELECT DISTINCT` that `findAllByOwner_IdOrderByCreatedAtDesc` and `findByOwner_IdAndPlanDateOrderByCreatedAtDesc` carry today are removed along with those methods — that is the exact code behind issue 4 in `docs/implementation-issues.md`, and deleting it is safe only because nothing maps items on that path any more.

The fetch graph survives where it is genuinely required: `findByOwner_IdAndId` for detail, and a new graph-backed `findFirstByOwner_IdAndPlanDateOrderByCreatedAtDesc` for the latest-plan read.

## Generated API Contract

Add `springdoc-openapi-starter-webmvc-ui`. Most of the contract is inferred from the existing request and response records and their Bean Validation annotations; controllers need only enough annotation to describe status codes that springdoc cannot infer, such as the 204 on the latest-plan read.

`/v3/api-docs` and Swagger UI are disabled in the default profile and enabled in a new `application-dev.yml`.

The hand-maintained `docs/openapi.yaml` is replaced by a generated file, committed so the contract remains reviewable in diffs, and regenerated by a Gradle task. CI fails when the committed copy differs from what the code produces, which is what makes drift impossible rather than merely discouraged.

`docs/api.md` stays hand-written. It explains session and CSRF calling rules and shows worked examples — a calling guide, not a schema dump. It still needs editing in this milestone, because it documents the daily-plan list response that is becoming a page of summaries and gains the latest-plan endpoint. Its link to the OpenAPI file and the README's documentation section are updated to describe the generated artifact and the dev-profile Swagger UI, and the README's manual verification checklist picks up the 204 case.

## Observability

Add `spring-boot-starter-actuator`, exposing `health`, `info`, and `metrics`.

A `RequestIdFilter` in `common/observability` runs early in the chain. It reads `X-Request-Id` or generates a value when absent, puts it in the logging MDC, echoes it on the response header, and clears the MDC in a `finally` block so nothing leaks between pooled request threads. A `logback-spring.xml` adds the value to the existing readable console pattern.

`ApiErrorResponse` gains a nullable `requestId`, supplied by `GlobalExceptionHandler` from the MDC. The record is already annotated `@JsonInclude(NON_NULL)`, so this is backward compatible for any client that ignores unknown fields. This is the smallest change in the milestone and the one that most changes how debuggable the application is: a user reporting a failure can hand over an id that leads straight to the relevant log lines.

Micrometer, which arrives with Actuator, records:

- A timer around the provider call, tagged by outcome — success, provider error, or invalid response.
- A counter for retried attempts.
- A counter for ranking-validation rejections, tagged by reason.

That last one matters directly to the next milestone. 1.2.0 keeps the AI responsible for ordering while Java takes over placement, and the decision to keep trusting the model for ranking should rest on measured rejection rates rather than impressions.

## Security Exposure

`SecurityConfig` today permits register and login and requires authentication for everything else, with a 401 entry point. Two additions:

- `/actuator/health` is explicitly permitted, ahead of the `anyRequest().authenticated()` rule, so an orchestrator or uptime check can probe the application without credentials. Every other Actuator endpoint falls through to requiring a session, keeping metrics and environment details private.
- The springdoc paths are permitted by a separate, higher-precedence `SecurityFilterChain` bean annotated `@Profile("dev")`, whose security matcher covers only `/v3/api-docs/**` and `/swagger-ui/**`. Under the default profile that bean does not exist, so there is no permissive rule to audit and no accidental production exposure. The main chain keeps its ordering, its CSRF configuration, and `CsrfCookieFilter`.

## Error Handling

Status codes are unchanged: **400** for validation failures including the new pagination bounds, **401** unauthenticated, **403** forbidden, **404** for missing owner-scoped records, **409** for conflicts, and **502** for provider failures including exhausted retries.

The only change to the error contract is the added nullable `requestId`.

## Frontend

Changes are mechanical. Page navigation on plan history is the only one a user notices; everything else is the same screens fed from different endpoints.

- Plan history reads `itemCount` and `hasWarning` from the summary instead of deriving them from a full item array. `PlanHistoryList` currently renders `plan.items.length` and `plan.warning != null` and touches nothing else on a row, so the row markup is unaffected.
- Plan history consumes the page envelope and gains navigation between pages, driven by the envelope's `page` and `totalPages`. Without it, paginating the endpoint would silently hide older plans from anyone holding more than one page of them. Previous and next controls are enough; the list is chronological and has no search or filtering to preserve.
- The dashboard's today's-plan hook moves to `GET /api/daily-plans/latest` and maps **204** to an absent plan, feeding the existing empty state in `DailyPlanView`.
- `frontend/src/types/api.ts` gains `DailyPlanSummaryResponse` and `PageResponse<T>`, and the plan history type changes from `DailyPlanResponse[]`.
- Query keys and invalidation follow the existing pattern: generate and delete continue to invalidate both the history list and the latest-plan query.

## Testing Strategy

The existing style holds — Mockito for service behaviour, `@WebMvcTest` for HTTP and security boundaries, Testcontainers for persistence, ArchUnit for layering, and Vitest on the frontend.

The most valuable property this milestone adds is that migrations become self-checking. With Flyway plus `validate` running in the shared container, an entity field with no matching migration fails the build rather than surfacing later as a runtime error against a real database.

Highest-priority coverage:

- The application context starts against a migrated container with `validate` active, for both `@SpringBootTest` classes.
- Retry attempts the configured maximum on a 500 and on a read timeout, retries a 429, and does **not** retry a 401 — asserted by attempt count against a stub server, since the cost behaviour is the point.
- An exhausted retry still surfaces as **502** and persists no plan, preserving the 1.0.2 guarantee.
- The summary list returns correct `itemCount` and `hasWarning` values, and loads no items — verified by a persistence test that reads summaries outside the repository transaction, which would have caught issue 4 directly.
- Pagination defaults apply, `size` above the maximum returns **400**, and ordering is `createdAt` descending.
- The latest-plan endpoint returns **204** when no plan exists for the date, and the newest plan when several exist; `/latest` resolves to its own handler rather than binding as an `{id}`.
- `/actuator/health` answers unauthenticated, `/actuator/metrics` returns **401** unauthenticated, and the springdoc paths are absent without the `dev` profile.
- The request-id filter echoes an inbound `X-Request-Id`, generates one when absent, and the value reaches `ApiErrorResponse` on a failure.
- Frontend: plan history renders from summaries; page navigation requests the next page and disables itself on the first and last page; the dashboard shows its empty state on a 204.

## Risks

**Schema validation will surface existing drift all at once.** `validate` is strict about column types, lengths, and nullability. The `jsonb` warning column and the `varchar(32)` enum columns are the likely first offenders, so writing `V1` is an iterative exercise against a real database rather than a transcription of the entity classes. This is the milestone doing its job, but it should be planned as real work rather than a quick first step.

**Flyway makes a database mandatory at context startup.** Any `@SpringBootTest` now needs a reachable migrated database. The shared container addresses the two current cases; any new full-context test must use the same fixture.

**Removing the fetch graph is only safe together with the summary DTO.** If the projection and the graph removal land in separate steps in the wrong order, plan history regresses straight back to issue 4. They belong in one step.

**The OpenAPI freshness check can become noise.** If the generated document is not deterministic across runs, the CI check will fail on unrelated changes. Ordering needs to be stable before the check is enforced.

## Learning Priorities

Consistent with the parent spec, weighted toward operational Java and Spring practice rather than new domain modelling: versioned schema management and the difference between a baseline and a migration; Hibernate schema validation as a build-time guarantee; HTTP client timeout and retry design where retries cost money; Spring Data projections and pagination, and why a projection is preferable to fetching an aggregate you will not use; profile-scoped security configuration; and MDC-based request correlation.

## Suggested Decomposition

This milestone splits cleanly into steps that can each be verified on their own. Steps 2 through 5 depend on step 1 only for the ability to express schema changes, and none of them changes the others' behaviour.

1. **Flyway and the test fixture.** Dependencies, `V1` baseline, the shared `@ServiceConnection` container, `validate` in the test profile, removal of the `create-drop` override, and the README `ddl-auto` cleanup. Resolving validation mismatches belongs here.
2. **Provider timeouts and retry.** Properties, request factory, retry predicate, and the attempt-count tests.
3. **Plan summaries, pagination, and the latest-plan endpoint.** Projection, `PageResponse`, both endpoints, repository cleanup, and the matching frontend changes. The projection and the fetch-graph removal must land together.
4. **Generated OpenAPI.** springdoc, the dev profile, the Gradle generation task, the CI freshness check, and the documentation link updates.
5. **Observability.** Actuator, the security rules, the request-id filter and its appearance on `ApiErrorResponse`, the Logback pattern, and the provider metrics.

A type-1 plan derived from this spec should be marked **TDD suitable: partial**. The retry predicate, summary projection, pagination bounds, latest-plan status behaviour, request-id filter, and security rules are all naturally test-first. Writing `V1`, adding dependencies, and wiring the Gradle generation task are not.

## Roadmap Beyond 1.1.0

This spec is the first of an iteration whose remaining milestones are already designed in outline. Recording them here keeps the sequencing decisions with the work rather than losing them.

**1.2.0 — The scheduled day.** A plan stops being an ordered list and becomes a schedule. Persisted clock times with a day window, `DailyPlanItem` becoming a timed block that holds either work or rest, break placement from a focus cadence plus fixed breaks, fixed-time commitments, buffer time, and time-of-day placement preferences. Placement moves into a deterministic Java scheduler; the AI keeps supplying priority ordering, and `DailyPlanRankingValidator` narrows to policing ordering alone. Also settles plan identity — whether generating replaces, versions, or accumulates plans for a date — and delivers the day timeline UI. A persisted user-preferences surface arrives with it.

**1.3.0 — Progress and carry-over.** Actuals recorded against blocks, from which remaining effort is derived, letting unfinished work carry into a later day. Adds re-planning the remainder of a day and deadline feasibility warnings, and shows planned against actual on the timeline.

**1.4.0 — Dependencies and the multi-day horizon.** A task dependency graph with cycle detection and topological ordering layered over ranking, together with multi-day planning where long tasks split into sessions across dates. Dependencies constrain ordering but not placement, so they cost nothing to defer to here, and this is where their ripple effects across dates actually pay off.

Deferred with no milestone assigned: recurring tasks, subtasks and task hierarchy, audit timestamps and optimistic locking, generate rate limiting, task list pagination, and structured JSON logging.
