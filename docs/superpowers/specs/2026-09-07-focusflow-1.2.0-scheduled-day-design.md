# FocusFlow 1.2.0 Design — The Scheduled Day

Date: 2026-09-07

**Parent spec:** `docs/superpowers/specs/2026-05-14-focusflow-ai-design.md`
**Previous milestones:** `docs/superpowers/specs/2026-08-22-focusflow-1.0.2-design.md`, `docs/superpowers/specs/2026-08-26-focusflow-1.1.0-platform-hardening-design.md`
**Related UI spec:** `docs/superpowers/specs/2026-05-31-focusflow-frontend-ui-design.md`
**Domain glossary:** `CONTEXT.md`
**Roadmap:** `docs/superpowers/roadmap.md`

Decisions in this document are recorded as ADRs `docs/adr/0002` through `docs/adr/0017`.

## Purpose

Through 1.0.2 a Daily plan is an ordered list of tasks plus a typed-in minute budget. 1.1.0 hardens the platform so the next product change can reshape that aggregate without losing the schema. This milestone is that change: a plan becomes a clock schedule.

The AI still produces a ranking. A new deterministic Java scheduler places that ranking onto a work window, inserts cadence and fixed breaks, honors commitments and a trailing buffer, and splits long tasks into sessions. The dashboard and plan detail render those blocks on a vertical time rail. Generating a plan for a date replaces any existing plan for that date.

This is a design document, not an implementation plan. It assumes 1.1.0 is already built: Flyway owns the schema, generate is non-transactional until a short persist step, `planDate` is required, and plan history is paginated summaries.

## Goals And Non-Goals

Goals:

- Persist per-user scheduling preferences (work window, focus cadence, minimum session length, trailing buffer, optional peak window, labelled fixed breaks) with in-code defaults so a user who has never opened settings can still generate a plan.
- Persist dated fixed-time commitments and plan around them as unavailable time.
- Reshape `DailyPlanItem` into a timed block that can represent work, rest, a commitment, or buffer, or sit unplaced beside the clock with an explicit reason.
- Introduce a two-stage pure-Java scheduler: free intervals first, then placement with cadence splitting.
- Narrow the AI contract to a total ordering of every plannable task. The scheduler selects what fits. `DailyPlanRankingValidator` checks ids, completeness, uniqueness, and block order only.
- Enforce one Daily plan per owner and planning date. Regenerating replaces it.
- Render the day as a vertical time rail on both the dashboard aside and plan detail, with peak hours shaded and unplaced work listed beside the rail.
- Derive capacity and the shortfall warning from the schedule rather than from a typed minute count.

Non-Goals:

- No recorded actuals, remaining-effort derivation, carry-over, or mid-day re-plan. Those are 1.3.0, which reuses this scheduler with a shrunk window.
- No peak-aware placement. The peak window is stored and shaded; ranking order still fills the day front to back.
- No user timezone preference. Times are wall-clock `LocalTime` / `LocalDate`.
- No overnight windows, overnight breaks, or overnight commitments.
- No calendar sync, recurring commitments, or recurring tasks.
- No live timer, drag-to-reschedule, or manual block editing.
- No change to authentication, CSRF, Flyway policy, OpenAPI freshness, or observability from 1.1.0, except new metrics tags if a bounded ranking-rejection reason is added.
- Nothing from 1.4.0: task dependencies and the multi-day Gantt.

## Domain Language

Terms below amend `CONTEXT.md`. Prefer the glossary when they disagree with older specs.

**Work window**: The inclusive-start exclusive-end wall-clock span of one planning day (for example 09:00–18:00).
_Avoid:_ Available minutes, day length

**Focus cadence**: A maximum continuous focus stretch plus a cadence-break length. The scheduler splits work to honour the stretch and inserts cadence breaks between sessions.
_Avoid:_ Pomodoro (unless the user has configured 25/5)

**Minimum session**: The shortest work block the scheduler will emit as its own session, except when a leftover fragment is all that remains of a task and nothing earlier can absorb it.

**Fixed break**: A labelled recurring daily unavailable window stored on scheduling preferences (for example lunch 12:00–13:00).

**Commitment**: A labelled one-off unavailable window on a specific calendar date (for example a meeting). Not a Task.

**Trailing buffer**: The last N minutes of the work window reserved as contingency and rendered as a distinct block. Not available for placement.

**Peak window**: An optional wall-clock span shaded on the timeline. It does not change placement.

**Timed block**: One `DailyPlanItem` with a kind, a start and end, or an unplaced reason.

**Work session**: A placed work block for one Task. Several sessions of the same Task may exist in one plan. Session labels (`2 of 3`) are derived at mapping time.

**Unplaced work**: A work item that is in the plan but not on the clock, with reason `NO_ESTIMATE` or `OUT_OF_TIME`.

**Day capacity**: The total minutes of free intervals after subtracting fixed breaks, commitments overlapping the window, and the trailing buffer from the work window. Cadence breaks are not subtracted here; they consume capacity during placement.

**Required minutes**: The sum of known estimates on must-include candidates at generate time.

**Schedule snapshot**: The work window and peak window copied onto the Daily plan at generate time so later preference edits do not rewrite history.

**The plan for a date**: The single Daily plan for that owner and planning date. Generating again replaces it.
_Avoid:_ Latest plan for a date

## User Workflow

1. A user sets scheduling preferences, or skips that and keeps the in-code defaults.
2. Optionally they add commitments on the planning date.
3. They generate a plan for an explicit planning date. If a plan already exists for that date, they confirm replacement.
4. The backend loads plannable tasks and commitments, asks the model for a total ranking, validates ordering, runs the scheduler, replaces any existing plan for that date, and returns the timed plan.
5. The dashboard and plan detail show a vertical rail spanning the snapshot window: work sessions, cadence breaks, fixed breaks, commitments, and buffer, with peak hours shaded. Unplaced work sits in a companion list with a reason.
6. If must-include work is unplaced, a shortfall warning lists those tasks.

## Architecture

No change to the layered model. Controllers still delegate to services; services own transactions; repositories persist; cross-feature reads go through facades. Three additions:

- `com.focusflow.preferences` — preferences aggregate, defaults, and HTTP API.
- `com.focusflow.commitment` — dated commitments and HTTP API.
- `com.focusflow.schedule` — the two-stage scheduler as pure functions over immutable records. It must not depend on Spring, JPA, or `plan.dto`. `DailyPlanService` maps entities into scheduler input and scheduler output into entities.

Plan generation keeps 1.1.0's two boundaries. Non-transactional orchestration loads a generation snapshot (tasks, effective preferences, commitments for the date), calls the provider, validates ranking, and runs the scheduler. A short transactional persist step deletes any existing plan for that owner and date, reloads selected task references, and saves the new plan. A selected task deleted in that window still returns **409** and saves nothing.

`LayeredArchitectureTest` gains the same DTO rule for any new repositories. Preferences and commitment response types stay in their `dto` packages; repositories return entities or package-local projections.

## Schema

The next Flyway version after 1.1.0's `V1` is forward-only and destructive for plans. It needs the same backup-first README procedure 1.1.0 established for legacy adoption. Tasks, users, preferences, and commitments are not deleted.

### Destructive plan reset

1. Delete all rows in `daily_plan_items`, then `daily_plans`.
2. Drop `daily_plans.available_minutes` and `daily_plans.warning`.
3. Add a unique constraint on `daily_plans (owner_id, plan_date)`.

After this migration every Daily plan in the database has clock times, so the frontend has one rendering path.

### `daily_plans` columns after reshape

Existing: `id`, `owner_id`, `plan_date`, `created_at`.

Added:

| Column | Type | Notes |
|---|---|---|
| `window_start` | `time` not null | Snapshot of the work window start |
| `window_end` | `time` not null | Snapshot of the work window end |
| `peak_start` | `time` null | Snapshot; null when the user has no peak window |
| `peak_end` | `time` null | Snapshot; null when the user has no peak window |
| `capacity_minutes` | `int` not null | Day capacity at generate time |
| `required_minutes` | `int` not null | Known must-include estimates at generate time |

### `daily_plan_items` columns after reshape

Existing: `id`, `daily_plan_id`, `position`.

Changed:

| Column | Type | Notes |
|---|---|---|
| `task_id` | `bigint` null | Required for `WORK`; null for rest, commitment, and buffer |
| `kind` | `varchar(32)` not null | `WORK`, `CADENCE_BREAK`, `FIXED_BREAK`, `COMMITMENT`, `BUFFER` |
| `start_time` | `time` null | Set iff the block is placed |
| `end_time` | `time` null | Set iff the block is placed |
| `label` | `varchar(255)` null | Title for non-work blocks (lunch, standup, buffer) |
| `must_include` | `boolean` null | Snapshot for `WORK`; null otherwise |
| `unplaced_reason` | `varchar(32)` null | `NO_ESTIMATE` or `OUT_OF_TIME` |
| `unplaced_minutes` | `int` null | Remaining unplaced estimate; required when reason is `OUT_OF_TIME` |

Invariant, enforced in the service before persist (and by a check constraint where the database can express it): a row has either `(start_time, end_time)` or `unplaced_reason`, never both, never neither. Placed rows have `end_time` after `start_time`. `WORK` rows have a `task_id`. Non-work rows have a `label` and no `task_id`.

`position` remains the stable order: placed blocks by `start_time` ascending, then unplaced work in ranking order.

### New tables

**`scheduling_preferences`** — at most one row per user (`owner_id` unique). Columns: `work_day_start`, `work_day_end`, `max_focus_minutes`, `break_minutes`, `min_session_minutes`, `buffer_minutes`, nullable `peak_start` / `peak_end`. Absence of a row means in-code defaults apply; generating does not insert a row.

**`fixed_breaks`** — children of `scheduling_preferences`: `label`, `start_time`, `end_time`. Overlapping fixed breaks are rejected on write.

**`commitments`** — owner-scoped: `title`, `commitment_date`, `start_time`, `end_time`. Overlapping commitments for the same owner and date are rejected on write.

All new time columns are PostgreSQL `time` without time zone, matching `LocalTime`. Dates are `date`, matching `LocalDate`.

## Scheduling Preferences

### In-code defaults

Used whenever the owner has no preferences row:

| Field | Default |
|---|---|
| Work window | 09:00–18:00 |
| Max focus | 50 minutes |
| Cadence break | 10 minutes |
| Minimum session | 15 minutes |
| Trailing buffer | 0 minutes |
| Peak window | none |
| Fixed breaks | none |

`GET` always returns these effective values. A boolean `persisted` tells the settings page whether the user has saved.

### Validation on save

- `workDayEnd` is after `workDayStart`. No overnight window.
- `maxFocusMinutes >= minSessionMinutes >= 1`.
- `breakMinutes >= 0`.
- `bufferMinutes >= 0` and strictly less than the window length in minutes.
- Peak window, if present: start before end, and both lie inside the work window.
- Each fixed break: start before end, no overnight, unique label per user not required, no overlap with another fixed break.

Saving replaces the aggregate, including the full fixed-break list.

## Commitments

A commitment is not a Task and does not appear in the ranking. The scheduler treats its interval as unavailable, clipped to the work window, and emits a `COMMITMENT` block for the clipped span when the interval overlaps the window. A commitment wholly outside the window is stored but does not affect the plan.

Validation on write: start before end, no overnight, no overlap with another commitment of the same owner on the same date.

## The Two-Stage Scheduler

Both stages are pure functions. Tests construct records and assert records. No Spring context.

### Stage 1 — free intervals

Input: work window, fixed breaks, commitments for the planning date, trailing buffer minutes.

1. Start with `[workDayStart, workDayEnd)`.
2. Subtract each fixed break and each commitment, clipped to the window. Overlapping unavailable intervals merge.
3. Subtract the trailing buffer `[workDayEnd - bufferMinutes, workDayEnd)` (a no-op when buffer is 0). Where that slice is already unavailable, the remaining trailing free slice becomes the buffer; a fully covered buffer emits no `BUFFER` block.
4. Return the ordered free intervals, plus the labelled unavailable intervals so stage 2 / persist can emit `FIXED_BREAK`, `COMMITMENT`, and `BUFFER` blocks.

Day capacity is the sum of free-interval durations after step 3.

Idle gaps that later arise because a cadence break does not fit in a leftover sliver are not computed here.

### Stage 2 — placement

Input: free intervals from stage 1, ranking (total order of plannable tasks with estimates and must-include flags), `maxFocusMinutes`, `breakMinutes`, `minSessionMinutes`.

Walk the ranking. Maintain a cursor in the free intervals and a `focusClock` of continuous focus minutes since the last cadence or fixed interruption.

For each task:

- **No estimate.** Emit one unplaced `WORK` item, reason `NO_ESTIMATE`. Consume no time.
- **Has estimate.** Place `remaining = estimate` as follows, then if `remaining > 0` emit one unplaced `WORK` item, reason `OUT_OF_TIME`, `unplacedMinutes = remaining`. A task may therefore have placed sessions and an unplaced remainder.

Placement loop while `remaining > 0` and free time remains:

1. If the cursor sits at the end of the current interval, advance. Crossing a labelled unavailable interval resets `focusClock` to 0.
2. If `focusClock == maxFocusMinutes`, try to insert a cadence break of `breakMinutes` at the cursor. If the current interval has at least `breakMinutes` left, emit `CADENCE_BREAK`, advance, reset `focusClock`. If not, leave the sliver idle (no block), advance to the next interval, reset `focusClock`.
3. Let `chunk = min(remaining, minutes left in this interval, maxFocusMinutes - focusClock)`.
4. **Absorb short tails.** If this chunk would be a non-final session shorter than `minSessionMinutes` (`chunk < minSessionMinutes` and `chunk < remaining`), do not start it. Instead extend the previous session of *this* task when that session is still in the same free interval (so extending it only exceeds the cadence maximum, not a fixed interruption). If there is no such session, skip this sliver as idle and continue at the next interval.
5. **Final short piece.** If `chunk == remaining` and `chunk < minSessionMinutes`, extend the previous same-interval session when one exists; otherwise place the short session rather than leaving the last minutes unplaced while free time exists.
6. Emit or extend a `WORK` block, advance the cursor, add `chunk` to `focusClock`, subtract from `remaining`.

After the ranking is exhausted, unused free time stays empty on the rail (no filler blocks). Emit the labelled unavailable blocks from stage 1 into the item list.

Peak window is not an input to either stage.

### Worked examples

Assume window 09:00–18:00, cadence 50/10, minimum session 15, lunch 12:00–13:00, buffer 0.

- **120-minute task at 09:00.** Sessions 09:00–09:50, 10:00–10:50, 11:00–11:20 with 10-minute cadence breaks between. Tail 20 ≥ 15, so it is its own session.
- **113-minute task.** Sessions 09:00–09:50 and 10:00–11:03. The 13-minute tail is absorbed into the second session, which exceeds 50.
- **55-minute task.** One session 09:00–09:55. The 5-minute tail is absorbed into the first session.
- **Must-include 8 hours of estimates, 7 hours of day capacity.** Place in ranking order until free intervals are gone; remaining must-include estimates become `OUT_OF_TIME` unplaced items. The rail never extends past 18:00.
- **Unestimated must-include.** Companion list, reason `NO_ESTIMATE`; warning fires.

## AI Ranking And Validation

The provider returns the existing JSON shape: ordered items of `taskId` and `position`. The prompt change is the contract:

- List every plannable task, including status, as today.
- Instruct the model to return **every** listed id exactly once, in block order (must-continue, then due/overdue, then optional), using the existing intra-block ranking guidance.
- Do not mention leftover minutes, optional-fit arithmetic, or clock times. Placement is not the model's job.
- `AiDailyPlanRequest` drops `availableMinutes`. The prompt may still mention the planning date.

`DailyPlanRankingValidator` rejects when:

- A task id is not in the candidate set.
- Any candidate is missing.
- Any candidate appears more than once.
- Walking the items, a later block appears before an earlier block.

It no longer computes leftover or optional overflow. Intra-block mis-order is still accepted. Rejection still surfaces as **502** and saves nothing. Ranking-rejection metrics keep a bounded reason enum; add `DUPLICATE_TASK` and `MISSING_OPTIONAL` (missing must-include reasons stay).

## Generation Flow

1. Require `planDate`. Load plannable tasks. Empty set → **400** `no plannable tasks available for planning`, no provider call.
2. Load effective preferences and commitments for `planDate`.
3. Classify candidates into blocks 1 / 2 / 3 as in 1.0.2. Compute `requiredMinutes`.
4. Call the provider with the full candidate list. Validate ranking.
5. Run stage 1, then stage 2.
6. Persist, replacing any existing plan for `(owner, planDate)`: snapshot window and peak, `capacityMinutes`, `requiredMinutes`, placed and unplaced items. Return plan detail.

`createdAt` on replace is the new generation time.

## Shortfall Warning

No persisted warning JSON. The mapper builds `warning` as null unless at least one `WORK` item has `mustInclude == true` and a non-null `unplacedReason`.

When non-null:

- `requiredMinutes` and `capacityMinutes` from the plan snapshot.
- `outOfTimeTasks` — must-include items with reason `OUT_OF_TIME`: `taskId`, `title`, `unplacedMinutes`.
- `unestimatedTasks` — must-include items with reason `NO_ESTIMATE`: `taskId`, `title`.

Optional unplaced work does not create a warning. History `hasWarning` is true when that mapped warning would be non-null (an exists-query on must-include unplaced items, or an equivalent persisted bit computed at generate time if the projection is easier that way). The bit, if used, is not a second source of truth for the detail payload.

## API Shape

First-party product API; frontend and backend change atomically. OpenAPI snapshot updates with the implementation.

### Plans

**`POST /api/daily-plans/generate`** — body `{ "planDate": "YYYY-MM-DD" }` only. `availableMinutes` is rejected if sent (`400`). Response is extended `DailyPlanResponse`. Replaces the existing plan for that date.

**`GET /api/daily-plans/latest?planDate=`** — unchanged path. Returns the one plan for that date, or **204**.

**`GET /api/daily-plans`**, **`GET /api/daily-plans/{id}`**, **`DELETE /api/daily-plans/{id}`** — unchanged paths. Summary drops `availableMinutes`, adds `capacityMinutes`. Detail uses the extended item shape.

Extended `DailyPlanResponse`: `id`, `planDate`, `createdAt`, `windowStart`, `windowEnd`, `peakStart`, `peakEnd`, `capacityMinutes`, `requiredMinutes`, `warning`, `items`.

`DailyPlanItemResponse`: `position`, `kind`, `startTime`, `endTime`, `label`, `mustInclude`, `unplacedReason`, `unplacedMinutes`, `sessionIndex`, `sessionCount`, `task`.

`sessionIndex` / `sessionCount` are 1-based and present only on placed `WORK` items that share a task with at least one other placed `WORK` item in this plan. Unplaced remainders are not counted as sessions.

`DailyPlanSummaryResponse`: `id`, `planDate`, `createdAt`, `capacityMinutes`, `itemCount`, `hasWarning`. `itemCount` counts every persisted item.

### Preferences

- `GET /api/scheduling-preferences` — **200** with effective values and `persisted`.
- `PUT /api/scheduling-preferences` — upsert; **200** with persisted values (`persisted: true`).

### Commitments

- `GET /api/commitments?from=&to=` — owner-scoped, inclusive date range, required query params, **400** if missing or `from > to`.
- `POST /api/commitments` — create.
- `PUT /api/commitments/{id}` — replace title and window; date is immutable (change of date is delete + create). Missing or other-user **404**.
- `DELETE /api/commitments/{id}` — **204**. Missing or other-user **404**.

CSRF follows other state-changing requests.

## Error Handling

Existing codes stay. Additions:

- **400** — invalid preferences or commitments (overlap, overnight, bounds); generate body still containing `availableMinutes`; commitment list range errors.
- **409** — selected task disappeared before persist, as in 1.1.0.

Replace-on-generate is not a conflict.

## Frontend

Follow the UI spec's confirmation, toast, alert, and query-invalidation patterns.

### Settings (`/settings`)

New authenticated route. Sidebar gains a Settings link. The page edits work window, cadence, minimum session, trailing buffer, optional peak window, and the list of fixed breaks. Saving `PUT`s the aggregate. Unsaved defaults render as the effective values with copy that they apply until saved.

### Commitments

On the dashboard planning column, a dated list for the browser-local calendar date: add, edit, delete with the same confirm-on-delete pattern as tasks. This is the only commitment UI in 1.2.0.

### Generate

`GeneratePlanCard` drops the available-minutes input. Primary action generates for the browser-local date. If `GET .../latest` already returned a plan, confirm replacement before calling generate. Success toast; invalidate latest-plan, history, as today.

### Day timeline

Replace the ordered list in `DailyPlanView` with a **vertical time rail** on both the dashboard aside and plan detail. Time runs top to bottom across the snapshot work window. Block height is proportional to duration. Cadence breaks, fixed breaks, commitments, and buffer use distinct treatments (buffer is an outlined empty slice). The peak window, when present on the snapshot, is a shaded band. Hour labels sit in a gutter. Ten-minute cadence breaks may be too short to label; colour is enough.

Unplaced work renders in a companion list below the rail, with reason copy: "no estimate — add one to put it on the clock" or "out of time" plus unplaced minutes. Must-include unplaced items also appear in the shortfall alert above the rail.

Empty state, loading skeleton, and error retry stay. Plan history rows use `capacityMinutes` and `hasWarning`; they do not grow a mini-rail.

## Testing Strategy

Existing style: JUnit 5 for the scheduler as plain unit tests, Mockito at service level, `@WebMvcTest` for HTTP and security, Testcontainers for persistence and the unique constraint, ArchUnit for the new packages, Vitest for the rail, settings form, generate confirm, and warning.

Highest-priority coverage:

- Stage 1: window minus lunch minus buffer; overlapping commitment and lunch merge; commitment wholly outside the window ignored; zero buffer is a no-op.
- Stage 2: the three splitting examples above; cadence break that does not fit a sliver leaves idle time; unestimated tasks never occupy the clock; overflow stays inside the window and emits `OUT_OF_TIME`; optional work after capacity is unplaced and does not warn.
- Ranking validator: missing optional id, duplicate id, block-order break, unknown id; leftover/optional-overflow cases from 1.0.2 no longer reject.
- Preferences GET without a row returns defaults (`persisted: false`); PUT then GET round-trips; overlapping fixed breaks 400.
- Commitments overlap 400; owner scoping 404.
- Generate with only `planDate` replaces an existing plan; unique constraint holds; 409 on deleted selected task; generate still 400 when no plannable tasks.
- Migration: post-migrate `daily_plans` is empty; Hibernate `validate` passes.
- Frontend: rail renders placed kinds against the snapshot window; companion list shows both reasons; generate confirms when a plan exists; settings save sends the aggregate.

## Risks

**Destructive migration is irreversible without the backup.** Pre-1.2.0 plans are deleted. The README must say so in the same tone as 1.1.0's adoption procedure.

**1.1.0 must ship first.** This spec's schema is the next Flyway version, not a rewrite of `V1`.

**Absorb-vs-idle edge cases will dominate scheduler tests.** The rules above are the spec; an implementation that invents a third behaviour for a 14-minute sliver at lunch is a bug even if it "looks nicer."

**Replace deletes 1.3.0's future actuals.** 1.3.0 must confront confirmation (or refuse replace when actuals exist). 1.2.0 only confirms because the plan is still disposable.

**Display-only peak hours can look like a broken preference.** Settings copy must say the band is visual until a later milestone.

## Learning Priorities

Consistent with the parent spec, weighted toward a testable domain function in Java: modelling time as `LocalTime` intervals, splitting a greedy placement algorithm into two stages so failures pin to one job, narrowing an AI boundary until the model cannot do arithmetic, and replacing a JSON snapshot with facts already stored as rows.

## Suggested Decomposition

A type-1 plan derived from this spec should be marked **TDD suitable: partial**. The scheduler, ranking-validator narrowing, preference and commitment validation, replace-on-generate, and unique constraint are naturally test-first. The Flyway SQL, settings page layout, and rail CSS are not.

1. **Schema.** Destructive plan reset, unique constraint, reshaped items, new tables, Hibernate validate, README backup procedure.
2. **Preferences and commitments.** Defaults, CRUD, validation, owner scoping. No generate change yet.
3. **Scheduler.** Stage 1 and stage 2 as pure unit tests, then wiring.
4. **Generate rewrite.** Total-order prompt, narrowed validator, replace persist, derived warning, API/DTO/OpenAPI updates.
5. **Frontend.** Settings route, commitments on the dashboard, generate confirm, vertical rail, warning and companion list.

Steps 3 and 4 are the product; 1 is the precondition; 2 can overlap 3; 5 consumes 4's contract.
